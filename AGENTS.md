# Architecture rules
- Aviation public-policy data and shared wording live in aviation-policy and remain separate from payment enforcement so copy updates cannot silently change charges.
- The main aviation overview and its initial-HTML fallback share aviation-overview content so crawler-visible service, coverage and quote information cannot diverge from the page.
- Aviation supporting pages use serviceLandingPages for distinct metadata, scope questions and related links in both the template and initial-HTML fallback; aviation breadcrumbs point to /services in both representations and access wording comes from aviation-policy, while scoped optional fields preserve other services' rendering.
- Aviation initial HTML replaces shell schemas with one existing business and a scoped Service provider reference, preventing inherited homepage claims; sitemaps omit inferred source/file timestamps because those do not prove significant page changes.
- Preserve protected admin destinations in an encoded auth return URL validated by auth-return; destination pages retain role checks and appointment reads stay behind authentication so navigation intent never grants access.
- Calendar exports and feeds share appointment-calendar Chicago wall-time conversion and emit UTC RFC 5545 instants; classification uses the Chicago calendar day without altering each view's status rules, so device zones cannot shift appointments.
- Customer appointment overview renders the next booking once ahead of preparation guidance, reuses current booking dialog actions, and links history/receipts to the existing records view; admin appointment presentation remains separate.
- Password recovery uses the existing auth provider's recovery session and updateUser, never custom reset tokens; validate recovery intent and current user, clear the local session after saving, and preserve only safe account destinations.
- Generate appointment email actions through appointment-links on the production origin; verify the stored appointment capability (including supported legacy random formats) or authenticated ownership, then reuse customer writers. Management reads/slots never mutate, old mutation endpoints are retired, and verified token writes include token compare-and-set to reject revocation races.
- Booking progress maps the existing screen IDs by service branch; the selection summary derives directly from current booking state and the shared payable-total calculation, never a separate price or selection store.
- Public /book and /auth responses use utility-route-seo in postbuild-seo and SEOHead for matching initial/rendered noindex metadata; never prerender authenticated portals, and allow utility crawling so noindex is readable.
- Outside-hours creation requires explicit internal-form opt-in and a server-verified admin role; public/client scheduling never opts in, so owner exceptions cannot widen customer hours.
- Store the featured Google review selection as one atomic, admin-only editable collection in public.featured_google_reviews; public readers receive only complete selections, preventing partial updates across pages.
- Keep review validation and access in one repository, and render public reviews through GoogleReviews on every page so content and behavior cannot diverge.
- Keep homepage FAQ answers force-mounted but hidden when collapsed, and wait for data-crawl-pending to clear before prerender capture so initial HTML contains real content without changing accordion behavior or adding review schema.
- Keep account email dispatch in the scaffolded managed SDK handler; preserve independent Resend feature senders so the email update does not change their provider or content.
- Record booking changes via the bookings_audit database trigger into public.booking_audit_log, never from app code, so every change path (app, functions, admin) is captured.
- Client balance and card-wallet consume the service-only portal_booking_balance RPC also used by the locked reservation trigger; successful identity-matched ledger credits are authoritative, quote-only/stale deposit evidence requires review, and saved payable totals never gain a second fee. Stage unauthorized migrations outside managed migration history.
- Keep card data in Stripe; use the authenticated card-wallet function and durable per-booking authorization/reservation guards for balance charges, refusing ambiguous ledgers and uncertain retries to avoid unauthorized or duplicate payments.
- Settle portal charges atomically with a service-only database function and serialize payment/deposit writes on the booking lock so ledger, receipt and booking payment state cannot diverge.
- Publish customer service notes separately from internal notes, and keep documents protected by booking ownership so staff-only content never appears in the customer portal.
- Render customer appointment photos through AppointmentPhotos using short-lived private URLs, with distinct before/after groups and retryable loading, so failures never appear as missing records.
- Store reminder preferences and STOP suppression durably, and claim each appointment/channel/time reminder before dispatch through existing Resend and Twilio providers to honor consent and prevent duplicate sends.
- Authenticate reminder cron callbacks with a private service-only scheduler credential; never embed tokens in cron definitions or expose the credential through customer access.
- Public prices come only from src/lib/pricing.ts (active service_packages, membership_plans, and the booking flow's ceramic tiers) so pages and booking cannot contradict each other.
- Booking uses active authoritative package/add-on rows with shared booking-pricing cent arithmetic and vehicle resolution; checkout charges persisted bookings.total_price without re-adding add-ons or included fees, so the quoted and collected amounts agree.
- Each public page emits exactly one LocalBusiness JSON-LD (from localBusinessSchema, referenced elsewhere by @id); main.tsx clears prerendered JSON-LD before Helmet re-adds it, so schemas never duplicate after hydration.
- Legacy /services/* and /terms URLs are served as noindex canonical+refresh stubs by postbuild-seo (static hosting can't send 301s) plus client Navigate routes; internal links always use the keyword landing URLs.
- Customer reschedules go through the reschedule-booking function, which rechecks ownership, notice, hours, blocked dates, and capacity using shared reschedule-rules, and only saves if the appointment hasn't changed since the customer loaded it; the browser never writes the new time directly.
- Customer cancellation/rescheduling commits use a service-only compare-and-set RPC that atomically enqueues immutable owner-alert content with fixed recipients; leased per-channel dispatch bounds retries and holds uncertain SMS for review, so crashes cannot lose saved-change alerts or blindly duplicate messages.
- Customer cancellations use cancel-customer-booking for authenticated ownership, current-status/calendar-date checks and atomic compare-and-set; preserve payment fields and append reasons to notes, so cancellation cannot create financial actions or overwrite a changed appointment.
- Owner alert outbox wakes on enqueue and arms retries only while work remains using the existing private scheduler credential; stage SQL/configuration until release is authorized so preview work never modifies production scheduling.
- The /services directory content and head metadata come from services-directory-seo, shared by ServicesPage and the postbuild initial HTML, so the indexable hub's crawler and rendered versions cannot diverge.
- RV (rv-seo), car (car-seo) and boat (boat-seo) hub/supporting pages share content between rendered pages and postbuild initial HTML; inclusions mirror active packages/add-ons, teasers omit ceramic durations, and unavailable configs are noindex,follow without Service schema or sitemap entry.
- Prerender capture waits for Helmet's data-rh head tags, and postbuild-seo keeps one of each owned head tag (the page's robots wins) and adds a minimal Service node to service pages only when missing, so captured and empty-shell HTML agree.
